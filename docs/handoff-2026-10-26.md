## Candidate capabilities: user selection required

These are product suggestions based on the current personal workflow, not an approved roadmap. Select one small capability and validate it before expanding several areas at once.

| Proposed order | Capability | Value | Initial scope and decisions | Acceptance criteria |
| --- | --- | --- | --- | --- |
| 1 | Edit sent questions and regenerate replies | Revise a question and continue, or regenerate an unsatisfactory answer. | The completed editing fix concerns conversation titles, not message editing. Decide what happens to later messages when editing an earlier question: truncating and answering again is simpler; keeping conversation branches requires additional data structures. Also decide whether an old answer survives failed regeneration. | Subsequent requests contain the intended context; canceling leaves history unchanged; stopping, failures, and refresh preserve consistent records; replies never enter another conversation. |
| 2 | Complete backups and import restoration | Extend the current export feature into a restorable personal backup. | Start with versioned JSON. Distinguish append from replacement, handle ID conflicts, validate before import, and preview counts. Do not overwrite existing records by default. | A round trip restores titles and messages; invalid files leave data unchanged; repeated imports follow a documented and tested policy. |
| 3 | Conversation search and pinning | Find earlier conversations as the list grows. | Decide whether search covers titles only or message text too. Pinning can be scheduled separately; tags, folders, and archiving need not be bundled into the first change. | Selecting a result restores the correct context; clearing the query restores the list; empty results are understandable; pinning persists across refresh if implemented. |
| 4 | Conversation-specific assistant settings or model selection | Adapt response preferences or models to different tasks. | These can be separate features. Verify model candidates and quotas using official sources. Restrict allowed values on the server, keep credentials server-side, and decide when changed settings take effect. | Settings affect only the intended conversation and survive refresh; invalid models or parameters are rejected; errors explain what the user can do. |
| Later | Image or file questions | Support additional source materials. | First choose images, text, or PDFs and check model support, file size limits, and storage behavior. The current pipeline validates and serializes text-only messages; adding an upload button alone is insufficient. | Uploads, requests, rendering, persistence, and failures work together; tests use synthetic files rather than real user files. |
| When needed | Accounts, a database, and cross-device synchronization | Share personal history across devices or progress toward a multi-user product. | The user currently chose a local personal edition. Establish cross-device and public-access requirements before selecting authentication, storage, and deployment. Connecting a database alone does not complete productization. | User records are isolated; local-history migration can be checked; synchronization conflicts have clear rules; server authorization and usage limits are validated. |

For the next session, first establish whether the priority is improving individual conversation interactions or managing and restoring history. Prioritize candidate 1 for the former; candidate 2, followed by candidate 3, for the latter. Advance the final item only when the user asks for cross-device or multi-user usage.
